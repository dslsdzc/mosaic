# Mosaic 生态策略与差异化定位设计

> 日期:2026-08-25
> 状态:已确认(经头脑风暴逐节评审);方向性 spec(不涉及实施级 API 细节,指导后续里程碑)

## 1. 定位与背景

本 spec 记录 Mosaic 的外部验证结论与差异化定位。触发:实际 mod 开发者/整合包优化者的反馈对话(2026-08-25)+ 生态痛点调研(2026-08-25 网络检索)。

外部验证的核心反馈(朋友视角,普通 mod 开发者):
- "太实验性,没看到让我放弃 forge 的欲望"
- "跨版本稳定对作者没用,适配习惯了"
- "热更新不必要,folia 已有"
- "没经过生产环境考验,实际性能没实测过"
- "mixin 是我的命"——mixin 生态不可兼容是定位选择,不是可绕过的障碍

生态痛点调研(2026 实证,来源见 TODO.md 与对话记录):
- **适配税**:版本更新数月一次,作者 75% 时间重复适配,25% 做新功能;
- **停更即死**:mod 生命周期 = 作者生命周期(学业/健康/工作/社区压力退圈 → 适配链断裂 → 作品死亡);
- **崩溃无隔离**:一个 mod 的 bug 崩全家 → 停更下架;
- **兼容性地狱**:几百个 mod 兼容性手工管理无法自动化;mixin 是主要技术根源(两 mod 注入同一方法 → 字节码级硬崩溃),另有全局状态/注册表顺序假设;
- **Vulkan 换引擎(2026 当下)**:Mojang 弃用 OpenGL,作者重写 8000 行渲染代码,渲染类 mod "一夜之间废代码"。

## 2. 差异化定位(三维)

| 维度 | 命题 | 实证 |
|---|---|---|
| **时间** | 一次编写,全版本运行——适配税归零;**作品寿命 ≠ 作者寿命**(停更 mod 仍可运行) | 1.8.9↔26.2 双代契约同套件全绿;1.12/1.20.1 死水区(生态数据) |
| **资源** | 工作集内存 + 零启动成本(2 万 mod ≈ 10s 启动,架构推算) | 10M 冷函数 RSS 增量 0.12MB、S1-S5 门禁 |
| **观测** | 函数级确定性归因(非采样推断)——精确到"哪个事件、哪个函数、多少次、多少时间" | 事件监听器通道(M9)已交付;spark 为采样 profiler |

**核心命题:让 mod 活得比作者久。** 生态最大的痛不是"适配累",是"作品生命周期 = 作者生命周期"——作者退圈时开源、移交、求人接手,本质是版本绑定让作品活不过作者。Mosaic 的时间维度让"移交"变得不需要:代码版本无关,作品寿命与作者无关。

目标用户排序:**暂不排序**(方向 spec 只记录定位;优先序留给具体功能规划)。

## 3. 生态接入机制(三重边缘化 + 固化路径)

```
开发者构建(dev agent):受控 hook + 临时 hook(开放注入,冲突显式报告)
        ↓ PR 固化(混淆名核实 + 注入契约 + InjectCheck 门禁)
标准发行版:只含 SPECS 受控 hook(版本无关承诺 + 零自由注入面)
```

- **临时 hook**:类似 mixin 的开放注入能力(经 Mosaic 注入机制声明任意注入点,冲突 = 显式报告而非字节码级崩溃),仅存在于开发者/实验构建;
- **三重边缘化**:标准发行版制度性缺失 + 社区天然排斥(稳定性诉求)+ 大型整合包不用(生态稳定核心)→ 定位 = **作者个人试水通道**(开发体验),**实现优先级低**;
- **生态接入本体 = 受控 hook 面宽度**(SPECS 白名单):朋友的 mod 需要什么注入点,就固化什么注入点;
- 固化 = 只增不减的注入契约(与"API 缺口 Issue/PR 驱动"同一机制的两面)。

## 4. 受控 hook 面路线

- 现状:SPECS 11 类 14 方法(1.20.1 服务端注入点);
- 路线:PR 驱动补齐;每点 = 混淆名核实(server_mappings + javap)+ 注入契约 + InjectCheck 门禁;
- 跨版本适配由 Mosaic 承担(固化点版本无关——临时点标注当前版本有效,固化点才是版本无关承诺)。

## 5. 起步路径候选(不排序)

| 候选 | 内容 | 依赖 |
|---|---|---|
| 样板工程驱动 | GTNH 类整合包移植示范(AI 转换配方数据 JSON/ZenScript → Mosaic 格式),建立示范效应 | API 完整度 |
| 性能观测 | 函数级确定性归因("比 spark 更精准")——朋友明确需求,单服可演示,不依赖生态 | 独立 |
| 临时 hook 开发通道 | 三重边缘化,定位开发者试水 | 实现优先级低 |
| 1.20.1 Provider | Java mod 经稳定 API 在服务端跑的全链路 | 基础设施,方法论现成 |

## 6. 诚实边界(明确不承诺)

- **模组间兼容性**:零生态,无从谈起——不承诺、不宣传;
- **生产环境验证**:未跑过真实整合包/多人负载——"2 万 mod 10s 启动"是架构推算,不是生产实测;
- **mixin 生态**:不可兼得(定位选择)——生态接入靠受控 hook 面宽度,不是兼容 mixin;
- 临时 hook 不改变以上边界(三重边缘化本身就是"不承诺"的机制化)。

## 7. 与既有决策的关系

- **服务端优先**不变(M1);
- **只增不减 + API 有界性**:受控 hook 注入契约 = API 的一部分(固化 = 只增不减的注入面);
- **渲染层存档**(2026-08-25-render-layer-direction-design.md)= 引擎化方向的后置;Vulkan 换引擎事件是它的当下注脚(SDL3 GPU 支持 Vulkan——Mojang 换引擎,渲染 API 不变);
- **JVM 基线 25+/FFM 迁移**(已宣布)= 基础设施前提;
- **临时 hook 机制**与既有的 agent 注入机制(ClassFileTransformer + 自研 hook 点 + InjectCheck)同族,是它的开放注入扩展。
